What each setting does

  1. 01
    Request
    The scheduler reserves this much on a node.
  2. 02
    CPU limit
    The container is throttled above it.
  3. 03
    Memory limit
    The container is OOMKilled above it.
  4. 04
    Nothing set
    BestEffort: first to be evicted under pressure.

Sizing habits

Do
  • ✓Set requests from observed p95
  • ✓Memory limit = request for steady apps
  • ✓Use VPA recommendations as input
  • ✓Revisit after big releases
Avoid
  • ✕1 CPU / 1Gi everywhere
  • ✕Tight CPU limits on latency-critical paths
  • ✕Memory limit below startup peak
  • ✕No requests at all

Check before you guess

bash
kubectl top pods -n payments --containers

kubectl get pod api-7d9 -n payments \
  -o jsonpath='{.status.qosClass}'

kubectl describe pod api-7d9 -n payments \
  | grep -A4 "Last State"   # OOMKilled?

Throttling shows in container_cpu_cfs_throttled_periods_total, not in kubectl top.

How I size a new service

1Load test
2Observe p95 usage
3Set requests
4Set memory limit
5Watch throttling + OOMs
6Revisit monthly

Sizing is a loop, not a one-time YAML edit.

Key takeaway

Size from data, then keep watching.

  • Requests drive scheduling and HPA math
  • Memory limits kill, CPU limits throttle
  • Know your QoS class
